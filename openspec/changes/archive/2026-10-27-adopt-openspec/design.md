# Design

## Context

- The repository never used Agent OS or OpenSpec; there is nothing to migrate or remove.
- The module is a single flat root module: `main.tf` (all resources), `data.tf`, `locals.tf`, `variables.tf` (31 inputs), `outputs.tf` (29 outputs), `versions.tf`, plus `examples/minimal` and `examples/complete`. There is no `tests/` directory and no `checks.tf`.
- `CHANGELOG.md` is generated by git-cliff (`mise run changelog`, `.cliff.toml`) from commit subjects.

## Goals / Non-Goals

**Goals:**
- One planning system (OpenSpec), with engineering standards consumed from the pinned `quality`, `repository` and `terraform` stores, never copied.
- A baseline of the module's current contract that later changes can modify with deltas.
- Zero diff in `.tf` files, so the change cannot affect a consumer.

**Non-Goals:**
- Fixing inconsistencies found while writing the baseline, adding unit tests, or applying the store standards to the code. Specs describe what the code does today, including behaviour the standards may later reject.

## Decisions

### 1. Stores pinned through the terraform-module profile
`openspec/config.yaml` and `AGENTS.md` start from the canonical `terraform-module` profile; `references:` stay exactly as in the profile (`quality`, `repository`, `terraform`, each at a released tag). `mise run spec-setup` registers them once per machine.

### 2. Skills for Claude Code and OpenCode
The `openspec-*` skills are installed in `.claude/skills/` and `.opencode/skills/` and kept identical (`openspec update` after bumping the CLI). `CLAUDE.md` imports `AGENTS.md`; OpenCode reads `AGENTS.md` natively.

### 3. CI job `validate:specs`
`.gitlab/specs.yml` runs `openspec validate --all --strict`, the same command as `mise run spec-validate`, with the CLI version taken from `OPENSPEC_VERSION` in `.gitlab/global.yml` (kept equal to the `mise.toml` pin).

### 4. Baseline describes today's behaviour, warts included
Where code and its own descriptions disagree, the spec follows the code when the behaviour is clear and leaves the point out otherwise. The inconsistencies are reported in the change review, not fixed here.

### 5. Six capabilities, split by what the module manages
`module-contract` (versions, inputs, outputs, secrets), `instances` (the instance resource and its admin user), `databases-and-users` (databases, users, privileges), `network-access` (private network, ACL), `backups` (automatic schedule, manual backups), `read-replicas`. Each maps to one block of `main.tf`; `module-contract` carries what crosses the module boundary. No `security-guardrails` capability: the module has no `check` block, its guards are `precondition` and `validation` blocks owned by the capability they protect.

### 6. CHANGELOG stays generated
`CHANGELOG.md` is not curated by hand. Commit subjects read as CHANGELOG lines and `mise run changelog` regenerates the file at release, so `rules.tasks` and `operations.archive` in `config.yaml` and `AGENTS.md` say so instead of asking for an `## [Unreleased]` entry.
